# Independent security review findings — mage2mcp Phase 0

**Reviewer:** Independent security reviewer (not an author of the documents under review).
**Date:** 2026-11-18. **Baseline:** [research-baseline.md](../development/research-baseline.md) (2026-11-18).
**Scope:** [threat-model.md](../security/threat-model.md), [security-review.md](../security/security-review.md),
[ADR-0006](../adr/0006-authentication.md), [ADR-0012](../adr/0012-observability-and-audit.md),
[SECURITY.md](../../SECURITY.md), the four workflows in `.github/workflows/`,
[mcp-tools.md](../mcp-tools.md), and the Magento, Cloudflare and GA4 integration designs.
**Method:** adversarial read of each claimed control for testability, layer and effect; cross-document
consistency check; JWT pitfall checklist (RFC 8725); agent-specific abuse review; workflow review.
**Code status:** no implementation exists (`security-review.md:5`). Every finding is a design or
documentation defect, not a runtime vulnerability. Line numbers were verified against the working tree at
00:24 HKT; the tree was being edited concurrently, so later edits may shift them.

## 1. Threat-class coverage against the fifteen mandatory classes

All fifteen classes have a section in the threat model, so the coverage claim in
`docs/reviews/phase-0-report.md:133` is literally true. It is not uniformly substantive: five classes have
no threat ID for their real failure mode, and three headline controls are contradicted elsewhere in the
same document set.

| # | Mandatory class | Section | Assessment | Gap |
|---|---|---|---|---|
| 1 | Prompt injection | §5.1 | Covered, control overstated | Capability separation is false for shipped tools (F-04); approval channel defined twice (F-15) |
| 2 | Tool parameter injection | §5.2 | Covered | Conflicting SKU grammars (F-18); unconstrained schema fields (F-17) |
| 3 | Privilege escalation | §5.3 | Covered | Admin can grant itself a data role; no dual control (F-30) |
| 4 | Multi-tenant leakage | §5.4 | Partly covered | "Instance" has two definitions (F-09); cache key has no authorization dimension (F-03) |
| 5 | JWT forgery | §5.5 | Covered, strongest section | `type` claim enforced while marked `[U]` (F-16) |
| 6 | Token leakage | §5.6 | Covered | A read-scoped tool returns storage credentials (F-01) |
| 7 | SSRF | §5.7 | Covered, surface contradictory | "No URL tool" vs "media import is the URL tool" (F-32) |
| 8 | File upload | §5.8 | Partly covered | XLSX and gzip CSV reintroduce the bomb surface (F-10) |
| 9 | Malicious images | §5.9 | Partly covered | WebP cannot be re-encoded with the stated libraries (F-31) |
| 10 | API abuse | §5.10 | Covered | Cloudflare and GA4 budgets conflict (F-20); GA4 cost function unverified (F-21) |
| 11 | Rate-limit bypass | §5.11 | Covered | Subject-keyed design is correct; no gap found |
| 12 | Task duplication and replay | §5.12 | Covered | Redis write lock has no fencing token; acceptable for v1 |
| 13 | Task state tampering | §5.13 | Covered | State machine and CAS design are sound |
| 14 | Untrusted third-party responses | §5.14 | Partly covered | GraphQL 200-with-`errors` decodes as a zero result (F-28) |
| 15 | Supply chain | §5.15 | Partly covered | No SHA pinning (F-13); release privileges (F-14); SECURITY.md excludes the class (F-25) |

**Threat classes with no threat ID at all:** confirmation social engineering and approval fatigue (AB-6
covers only self-approval); property-level authorization in GA4 (not in the RBAC matrix); the R2 and
ClickHouse raw-log stores; cache authorization context; and verification of the service-token client
secret. These are gaps in the model, not just in the prose.

## 3. The four blocking findings in detail

**F-02 is the most damaging single line in the document set.** `magento.md:490` reduces the entire
confirmation protocol to a boolean the caller sets. The threat model, the tool catalog and the security
review all specify an opaque id approved by a different human on a separate surface; the integration design
for the module with the most destructive endpoints ships `confirm=true`. Four documents are normative for
the same tool surface, and an implementer reading the Magento design will build the boolean.

**F-04 removes the same control from the other direction.** Even if the approval ceremony is implemented,
the catalog and the review only require it for `destructive`. Price and inventory updates are `write`, which
`mcp-tools.md:133` defines as "reversible". A price change is reversible in principle and is still the
payload of the attack in §5.1. The §5.1 claim that no tool both reads untrusted content and writes is also
false for three shipped tools, so the "structural" mitigation is not structural.

**F-01 turns a read grant into storage credentials.** The documents already know that Logpush job
configuration contains destination credentials — that is why they require `Logs: Write`. The same
paragraphs then classify the tool as `read` and say Cloudflare tools are always read. A viewer-role agent
can retrieve the credential that controls the log archive.

**F-03 is a cross-privilege cache.** The cache key is well designed for tenant isolation and completely
silent about authorization context, while response shaping is explicitly role-dependent. The same key
serves masked and unmasked, row-capped and full responses.

## 4. Controls that are well designed

These are genuinely solid and should be preserved, not rewritten:

- **JWT verification design** (`threat-model.md:294`, `threat-model.md:449-464`). Algorithm allowlist with
  `none` and HMAC rejected before signature verification, `kid` as a lookup key only, `jku`/`x5u`/`jwk`
  ignored, redirects disabled, 3 s fetch timeout, 8 KiB token cap, exact `iss`/`aud`, 60 s skew and an
  `exp - iat` cap. This is a correct application of RFC 8725 and the strongest section of the set.
- **JWKS refresh budget** (`threat-model.md:168`). Single-flight, 10-minute cache, one refetch per 60 s,
  30 s negative cache, 1-hour stale-while-error, with a 1,000-random-`kid` test. Concrete and testable.
- **Egress design** (`threat-model.md:323`, `threat-model.md:504`). Resolve once, validate every address,
  dial the validated IP with `ServerName` set, normalise 4-in-6, refuse cross-host redirects, no proxy from
  the environment, validate instance base URLs at startup. The TTL-0 DNS-rebinding harness
  (`threat-model.md:325`) is a real test rather than a claim.
- **Strict JSON pre-parse** (`threat-model.md:249`). Duplicate keys, prototype keys, `UseNumber`, depth and
  array caps, 1 MiB `MaxBytesReader`, fuzz target. It correctly states that schema validation is structural
  and not semantic.
- **Rate-limit keying** (`threat-model.md:381`). Keyed on the verified subject, not the IP or the session,
  atomic Lua across replicas, strictest of subject/instance/deployment. Session rotation is irrelevant by
  construction, which is the right property.
- **Job state machine** (`threat-model.md:409`). Compare-and-set transitions, no client-writable status,
  cancellation re-read from the database, no `DELETE` for the runtime role.
- **Secret type** (`threat-model.md:308`). `String`, `GoString`, `MarshalJSON` and `Format` all redact,
  `Reveal` is lint-checked, and a canary test sweeps logs, panics and metrics. This is how a secret type
  should be built.
- **Cloudflare query construction** (`cloudflare.md:241-248`). Closed route table, no caller-controlled
  method or path, templates rejected at build time if they contain a mutation or subscription root, and a
  generated client with no `Mutate` method. Good code-level design, independent of the credential claim.
- **GA4 compatibility validator** (`ga4.md:196-198`, `ga4.md:241-247`). Three layers, observation dates on
  every rule, and a documented correction of its own baseline using live evidence. The best epistemic
  hygiene in the document set.
- **Magento write discipline** (`magento.md:29-31`, `magento.md:204-212`, `magento.md:252-257`,
  `magento.md:454-456`). "HTTP 200 is not correctness", per-transition idempotency keys, resumable state,
  read-then-send of the full extension block, and no automatic retry on a write timeout with read-back by
  natural key.
- **Data-quality semantics** (`cloudflare.md:499-509`, `ga4.md:430-440`). `bot_score` is null and never 0,
  `absent` is distinguished from `unknown`, sampling and staleness are labelled. This prevents the most
  likely real-world error in the whole product.
- **Candour about limits** (`cloudflare.md:279`, `SECURITY.md:15-18`, `security-review.md:5`). The
  documents say what they cannot do. Most of the findings above are places where another document did not
  match that standard.

## 6. Verdict

**Block.**

Blocking IDs: **F-01 through F-15** (all Critical and High findings). The design cannot proceed to
Phase 1 with a confirmation control that is specified four incompatible ways, one of which the agent can
satisfy itself; a read-scoped tool that returns storage credentials; a cache that ignores authorization
context; and a supply-chain and release path that contradicts its own threat model.

The document set is unusually strong on JWT verification, egress control, job state, GA4 data semantics and
honest self-reporting. The failures are concentrated where two documents describe the same control:
confirmation (threat model vs review vs Magento vs tool catalog), read-only (Cloudflare design vs credential
profile; Magento design vs ACL), audit (threat model vs ADR-0012), budgets (threat model vs integration
designs), and supply chain (threat model vs the workflows). That pattern suggests the threat model was
written as the authoritative design and the other documents were not reconciled against it.

What would move this to "Approve with changes":

1. One confirmation specification, cited by every document, with an opaque server-side id and no boolean.
2. An explicit Magento ACL manifest per mode and a startup probe, or the read-only claim downgraded to `[U]`.
3. `cloudflare.logs.jobs` made admin-scope with destination values redacted.
4. Authorization context in the cache key, and restricted fields never cached in clear.
5. SHA pinning in all four workflows and minimal per-job release permissions.
6. A decided audit failure policy and a required sink for regulated deployments.
7. Raw-log stores added to the threat model's scope and asset table.

Per-document disposition: threat model — keep, correct five overstated controls and renumber the ADRs;
security review — keep, adopt its confirmation protocol as normative and reconcile it with the threat
model; ADR-0006 — sound, confirm the `type` claim and the algorithm set; ADR-0012 — acceptable only after it
makes the decision it was written to make; SECURITY.md — good disclosure process, wrong scope carve-out and
ambiguous SLA; workflows — no SHA pinning and an over-privileged release; tool catalog — the weakest
contract (scopes, confirmation, schemas); integration designs — Magento contradicts the confirmation model,
Cloudflare overstates read-only, GA4 publishes a real tenant's data.

## 7. Limitations of this review

No implementation exists, so this review assesses design intent and documentation consistency, not runtime
behavior. No live Magento, Cloudflare or GA4 call was made; vendor behavior claims are taken from the
baseline and the evidence files, not re-verified. Git history, branch protection, environment reviewers and
repository settings were not inspected (no git commands were run), so the CI findings are limited to what
the workflow files show. Findings do not assert vulnerabilities in Magento, Cloudflare or Google products.
