# Architecture re-review — remediation round 1

**Reviewer:** independent architecture reviewer (did not author any reviewed document)
**Date:** 2026-11-19
**Baseline reviewed:** [architecture-review.md](architecture-review.md) (AR-01..AR-38), re-checked against the
current `architecture.md`, `module-boundaries.md`, `mcp-tools.md`, `database-design.md`,
`unified-analytics.md`, `development-plan.md`, and `adr/0002`, `0009`, `0011`, `0014`, `0015`, `0016`.
**Scope of this round:** status of AR-01..AR-21, verification of the specific fixes the remediation claims,
new contradictions introduced by the fix, and whether Phase 1 (registry, binding resolution, job enqueue) is
codable from these documents. AR-22..AR-38 (Medium/Low) are not re-scored except where the fix now depends on
them (noted inline).

## Method

1. Rebuilt the intended system from the current documents, not from the review's description of it.
2. For each of AR-01..AR-21, located the fix and cited the line that proves or refutes it. A finding is
   **Closed** only when the stated defect cannot recur from the current text; a fix that exists but is
   unusable as specified is **Partially closed**.
3. Adversarial pass on the new objects introduced by the remediation: `instance_bindings`,
   `binding_id` on permissions/jobs/confirmations, `core/jobs.Enqueuer`, `internal/admin`,
   `internal/logs`, the `platform.job.*` namespace, and the new error codes.
4. Implementability test: can Phase 1 write the registry, the binding resolution, and the enqueue without
   inventing a contract?

## Pattern in this round

The remediation moved the same defect one level down rather than removing it. Where the baseline said
"there is no table", the revision adds a table and leaves its invariants unstated: `instance_bindings`
exists but cannot be removed (N-14), `binding_id` exists but is invisible to the unique index and the
resolution order (N-03), `Enqueuer` exists but its `Task` does not (N-04), the approval surface exists but
its permission cannot be stored (N-02), and the approval package exists but has no import edge to the table
it writes (N-01). AR-04 and AR-13 show the same shape: a bound was added (50 children, narrowed freeze
claim) without the enabling contract (a required key, per-tool schemas).

Two consequences for the next round: every new column or package needs its invariant, its writer, and its
consumer named in the same edit; and a fix that adds an authorization dimension must be checked against the
resolution algorithm, not only against the storage schema.

## Can Phase 1 be coded from these documents?

- **Registry — no.** The catalog still carries no `capability`, `timeout`, `annotations`, or
  `requires_confirmation` per tool (`mcp-tools.md:52-68`, `:143-282`), and `platform.job.*` belongs to a
  namespace the grammar does not admit (`:34`). The registry self-test in `database-design.md:781-783`
  cannot be written against rows that cannot be constructed.
- **Binding resolution — no.** The config example is invalid (`architecture.md:221` vs `:238-239`), the
  validation rule ADR-0014 promises is unwritten (`adr/0014:75`), member optionality is undefined
  (`database-design.md:240-242`), and the authorization lookup cannot see `binding_id`
  (`database-design.md:303-304`, `:774-777`). A Phase 1 implementer must invent three contracts.
- **Job enqueue — no.** The interface exists (`module-boundaries.md:162-175`) but `Task` and `JobState`
  are undefined, so neither the caller nor the fake can be written without inventing the payload and
  scope contract (N-04).

## Verdict

**Block.**

The remediation is substantive and most of it lands: three of the five Criticals (AR-01, AR-02, AR-05) are
genuinely closed, AR-09, AR-11, AR-16, AR-18, and AR-19 close with evidence, and the new ADRs 0014–0016
are the right records. But one Critical-class defect survives inside the AR-03 fix: binding grants are
stored in the same unique-index slot as global grants and the documented resolution order never consults
`binding_id`, so a single binding grant authorizes a unified tool on every instance — the fail-open path
AR-03 was raised to close (N-03). Six further High findings are new contracts the remediation created and
left underspecified (N-01, N-02, N-04, N-05, N-06, N-07), and three tools still have no service method
(`magento.configurable.verify_storefront`, `magento.inventory.transfer`, `magento.import.report`).

Minimum set to unblock Phase 1, in order:

1. **N-03** — add `binding_id` to `tool_permissions_uq` and to the resolution order, make the stored `scope`
   authoritative, and fix `jobs_idempotency_uq`/`idempotency_keys` for `NULL` scope.
2. **N-06** — decide binding member optionality, write the binding validation rule, and correct the example
   config so it validates.
3. **N-04** — define `Task` and `JobState` in `module-boundaries.md` §4.3.
4. **AR-12 residual** — add the three missing service methods (or remove the three tools from the frozen
   catalog).
5. **N-01/N-02** — add `internal/admin` and `internal/logs` to the boundary tables and give the approval and
   PII permissions a storable representation.

N-05, N-07, N-08 through N-14 can be scheduled into Phase 1 without blocking the baseline, provided N-07 is
settled before Phase 2 starts. A second re-review is required for items 1–3 only, because each changes a
frozen data model or a core interface.
