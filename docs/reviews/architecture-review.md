# Architecture review — Phase 0 design baseline

**Reviewer:** independent architecture reviewer (did not author any reviewed document)
**Date:** 2026-11-19
**Baseline:** [research-baseline.md](../development/research-baseline.md) (baseline date 2026-11-18; tag legend `[V-live]`, `[V-docs]`, `[U]`)
**Scope:** `architecture.md`, `module-boundaries.md`, `mcp-tools.md`, `database-design.md`,
`unified-analytics.md`, `development-plan.md`, `adr/0001`–`adr/0013`.

## Method

1. Built the intended system from the documents: one Go binary plus worker, three source modules behind a
   `core` contract, a unified module over consumer-side interfaces, PostgreSQL for durable state, Redis for
   queues and limits, optional ClickHouse/R2 for raw logs.
2. Cross-checked every interface in `module-boundaries.md` §5 against a tool in `mcp-tools.md` §7, a table or
   column in `database-design.md`, and a phase in `development-plan.md`.
3. Checked the brief's non-negotiables: modular boundaries, capability-based registration, no universal
   execute tool, configurable product lifecycle, import idempotency and resume, multi-instance, raw logs out
   of PostgreSQL, unified metric semantics, extension without touching existing modules.
4. Checked ADR coverage and ADR-to-document agreement, and whether the frozen Go contracts are implementable
   as written.
5. Adversarial focus: cross-instance data access, confirmation semantics, job state transitions,
   timezone/currency joins, and whether `unified` can be built without importing module internals.

Findings are ordered by severity. Line numbers were verified against the files at review time.

## Cross-cutting analysis

**Cross-instance access is the systemic weakness.** Four independent findings (AR-03, AR-07, AR-08, AR-16)
are the same defect seen from four angles: the data model is instance-scoped, while the product's most
valuable features are cross-instance. Every table that would need a binding (`tool_permissions`, `jobs`,
`confirmation_tokens`, `sku_mappings`) has exactly one `instance_id`, and the YAML schema has no place to
declare a triple. The unified module is therefore specified at the semantic level (which is genuinely good)
but has no way to be authorized, scheduled, or stored.

**Confirmation is a ceremony without a participant.** AR-01, AR-25, and AR-32 compound: the nonce reaches
the requester, the database permits an approved state without an approver, and `resume` provides a
confirmation-free path to the same destructive effect. Read together, the write-safety story does not hold
even if each document is read charitably.

**The job model is designed but unreachable.** AR-05 (no legal enqueuer), AR-08 (no instance for platform
and unified jobs, no polling tool), AR-10 (retries ignore idempotency), and AR-33 (8 KiB results) mean the
async half of the architecture exists on paper only. Phase 2 depends on it for imports.

**Time and currency are handled well at the semantic layer and not at the storage layer.**
`unified-analytics.md` §4–§5 is the strongest reasoning in the document set — half-open intervals, DST
duration, no pro-rata splitting, no implicit conversion, mixed-currency nulls. But the neutral types cannot
express the nulls (AR-29), and `datasource_instances` has no zone or currency column even though the design
forbids filtering on `jsonb` content and every unified result must carry both.

**"Unified" cannot be implemented without importing module internals as specified.** AR-06 is the root
cause: the consumer interfaces are declared over module-owned query and result types. The document
acknowledges this and then leaves the neutral replacements undefined. Until the neutral type inventory
exists, `internal/unified` is either uncompilable or secretly coupled to all three modules, which defeats
ADR-0001's central claim.

**Phase sequencing has two unachievable exit criteria** (AR-20, AR-21). Both are detectable before coding
and cheap to fix now; after Phase 2 starts they become schedule risk.

## Strengths

- The no-escape-hatch rule is enforced consistently: no `execute_api`, no `execute_sql`, no raw GraphQL, no
  URL or SQL field in any schema. This is the right call and it is carried through every document.
- Raw logs are excluded from PostgreSQL for a quantified reason (F14, `database-design.md:60-63`) rather
  than by assertion; the storage split is defensible.
- `database-design.md` is unusually rigorous: `NOT NULL` plus `CHECK` instead of native enums, explicit
  jsonb inventory with an amendment rule, `NULLS NOT DISTINCT`, generated normalization column so the index
  cannot drift, and a named query-to-index table. Most projects do not have this.
- The unified-analytics non-equivalence table and the "no blended metric" rule are exactly the right
  posture for cross-source reporting, and the invariance rule for SKU mapping is testable.
- Failure semantics are honest: `verified_zero` versus `unknown`, `directional_only`, `requires_logpush`,
  and refusing a pro-rata GA4 day rather than fabricating one.
- The research baseline is used correctly: F18 (per-pair compatibility), F21 (no ecommerce), and F25
  (Open Source lacks import) are all reflected in the designs rather than papered over.

## Verdict

**Block.**

Five Critical findings must be resolved before Phase 1 code starts, because each one changes a frozen
interface or the data model rather than a detail:

- **AR-01** — no approval channel exists for confirmation; the write-safety control is unimplementable.
- **AR-02** — import idempotency is stated but not enforced by any constraint; duplicate writes are possible
  on the first concurrent submission.
- **AR-03** — the authorization model cannot represent a multi-instance unified tool; cross-instance reads
  are unscoped.
- **AR-04** — `magento.configurable.create` is a non-atomic 501-write synchronous call with no idempotency
  key.
- **AR-05** — the frozen import graph contains no legal path to enqueue a job, so the async design cannot be
  built.

High findings AR-06 through AR-21 should be resolved in the same revision pass; AR-06, AR-07, AR-12, and
AR-13 in particular are cheap to fix now and expensive after the interfaces are coded. Medium and Low
findings can be scheduled into Phase 1 without blocking the baseline.

Re-review is required after the blocking items are addressed, because AR-01, AR-03, AR-05, and AR-07 change
the contracts that every other finding is written against.
