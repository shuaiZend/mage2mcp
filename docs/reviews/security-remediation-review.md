## 4. Adversarial walks of the three controls named in the task

### 4.1 Confirmation flow

Trace: the agent calls `magento.product.delete` with no id → the gateway validates, hashes the canonical arguments, stores a
`pending` row keyed by `sha256(confirmation_id)`, and returns the id plus a summary (`threat-model.md:546`). The agent cannot
approve: there is no approval tool in the catalog, and the surface is the CLI or a human-only Access application
(`:547`). Approval requires a different `sub`, an unexpired row, a matching hash and the approval permission; the row moves
to `approved` (`:548`). Re-submission is one compare-and-set guarded by hash, identity and `expires_at`, and a second
attempt returns `confirmation_used` (`:417`, `:549`). The cap of 5 pending per subject and instance (`:552`) bounds fatigue.
This is a correct design and the earlier self-approval defect is gone.

What still breaks under pressure: (a) the approval predicate is not enforceable from the permission store, and the
permission has two names (R-02) — if the CLI writes `approver_hash` with direct database credentials, the sentence
"approval requires `confirmation:approve`" is documentation, not a check; (b) the summary a human reads is derived from
validated parameters, but for `magento.product.update` those parameters are read-modify-write from upstream content
(`threat-model.md:257` still claims capability separation per tool), so an attacker who controls a product name still shapes
part of what is approved — F-28 is unchanged and is not in this round's scope; (c) nothing binds the approval surface's
session to a second factor beyond the Access policy, which is acceptable for v1 but should be named in §6.3.

### 4.2 Cloudflare credential isolation

Trace: a refactor or dependency obtains the analytics client. The log-inspection credential lives in a separately
constructed client with its own transport, base URL and closed route table of two GETs, and the analytics client holds no
reference to it (`cloudflare.md:280-296`). A compromised *binary* still reads both, and the document says so (`:295-296`)
rather than claiming an OS boundary. `shared_token_instances` is "declared, not verified" (`:317`) and startup cannot detect
a silently added write scope (`:319`) — both are accepted and visible in the capability report, which is the right
disposition. The isolation control survives adversarial reading; the remaining defect in this area is documentation drift
about the raw-log store (R-07), not the credential design.

### 4.3 Audit fail-closed path

Trace: a write call inserts an intent row before the handler runs; if that insert fails, nothing executes
(`threat-model.md:570`). If it succeeds and the terminal row later fails, the gateway returns the result with
`audit_state=pending` rather than an error, and a crash between the rows is reconciled by reading the entity back from
upstream. That is the correct shape — the gate is the intent row, and the completion record is not allowed to turn a
successful write into a retry.

The path fails in two places. First, a denied call writes a single row with `state=denied`, and the schema's CHECK does not
permit that value (R-03), so the one row that proves the denial cannot be inserted — denials are the detection signal for
T-17, T-18 and the injection corpus, which makes this the worst possible audit gap. Second, ADR-0012 still instructs the
gateway to return `internal` when an audit write cannot be persisted (R-04); after a successful upstream write that invites
the retry, and the duplicate is caught only if the caller supplied an `idempotency_key`, which the design makes optional
(`threat-model.md:417`). The two documents must be reconciled before the writer is coded, not after.

## 5. Controls that should be preserved in the next edit

These are genuinely sound and the remediation should not churn them:

- **Confirmation core** (`threat-model.md:544-552`, `adr/0014:42-49`) — opaque id, separate human surface, distinct
  approver, hash binding, single use, 300 s/900 s, pending cap. Only the permission name and storage need fixing.
- **Service-token model** (`threat-model.md:505-517`) — one validator, no secret in the gateway, no comparison path, edge-side
  rotation and revocation. The cleanest resolution of a messy problem in the set.
- **Replay rule** (`threat-model.md:498`) — detection on `(token hash, session id)` with concurrent requests explicitly
  allowed, plus a test that asserts they succeed (`:663`). It resists the "weaken it to a no-op" failure.
- **Cloudflare route table and isolation table** (`cloudflare.md:247-254`, `:280-286`) — closed route tables, no
  caller-controlled method or path, templates rejected at build time, separate client for the write-capable credential.
- **Magento ACL manifests and probe** (`magento.md:57-125`) — the probe-safe invalid-body design (a wrongly authorized call
  still fails validation) is a better control than the "probe and expect 403" the earlier review asked for.
- **GA4 property grant and bounded caches** (`ga4.md:501-523`, `:413-436`) — property as the tenancy boundary, per-property
  credential by default, LRU caps per entry class with the authorization scope in the key.
- **Audit two-row protocol** (`threat-model.md:570`) — once R-03 and R-04 are fixed, the intent/terminal split with
  read-back reconciliation is the right answer to "HTTP 200 is not correctness".
- **SHA pinning and provenance** (`release.yml:15-33`, `:105-108`) — 32/32 pinned, job-scoped permissions, attestation and
  cosign; only the gate and the lint job are missing.

## 6. Verdict

**Approve with changes.** No Critical finding remains and no new Critical was introduced. Seven of the ten High findings from the previous round (F-01..F-10) are closed, three are partially closed, and the confirmation, service-token, replay and R2/ClickHouse rework is sound; the Cloudflare guarantee is now stated honestly.

Four High findings are new or residual, and three of them are contract defects that will be built into code if Phase 1 starts now: the approval permission has two names and no stated storage (R-02), the deny-path audit row cannot be written (R-03), and the audit failure policy contradicts itself across ADR-0012 and the threat model (R-04). The release path (R-01) and the missing pinning policy job (R-05) remain supply-chain gaps.

## 7. Limitations

No implementation exists, so this review assesses design intent and document consistency. The tree was being edited during
this round (other remediation agents were writing to `docs/security/`, `docs/integrations/`, `docs/database-design.md` and
`docs/module-boundaries.md` while it ran), so every citation is pinned to the text read at the time of this pass; a later
edit can move a line without changing the finding. No live Magento, Cloudflare or GA4 call was made. Git history, branch
protection, environment reviewers and repository settings were not inspected (no git commands were run), so the release
findings are limited to what the workflow files show; `sha_pinning_required` may be set at repository level, which the files
cannot show. Findings do not assert vulnerabilities in Magento, Cloudflare or Google products.
