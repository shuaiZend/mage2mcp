# v0.11.7 release notes

**The persona pass.** Seven agents with different jobs — a store operator, a merchandiser, a
customer service rep, a finance controller, an integrator, a security officer and a data
analyst — each used the gateway the way their work actually uses it, rather than tool by tool.
They produced 101 findings; deduplicated, 85 were repaired.

The record is in [`docs/audit/persona/FINAL-REPORT-zh.md`](../audit/persona/) and the summary
in [`SUMMARY.md`](../audit/persona/SUMMARY.md) (both Chinese), with one report per role.

## The release blocker

A weight edit silently repriced the product.

`buildUpdatePayload` handed `pricingAttributesFromPointers` five values starting with `Weight`,
while the order table it aligns against starts at `special_price`. Every field shifted one slot:
weight became the sale price, special price became a start date, a start date became a cost, and
so on.

Reproduced on the production build: a product priced 100.00, updated with `weight: 9.99` and
nothing else, read back `special_price: 9.990000`. A routine weight edit put it on sale at 9.99
and nothing reported an error. The create path was correct, which is why only updates were
affected — and no test covered either helper.

## Money and documents

- **A credit memo or shipment carrying a comment was rejected outright.** Magento's
  `is_visible_on_front` is an integer; the gateway sent a boolean. Any "refund with a note"
  failed.
- **A partial refund refunded the whole shipping amount.** The gateway had no `shipping_amount`
  parameter, so Magento applied its default. Refunding one of two items returned the item plus
  the entire shipping charge, with nothing in the response to say so. It now takes
  `shipping_amount` and refunds remaining shipping only when the last units go.
- **Credit memos were not checked against the invoice's quantity**, so a refund could exceed the
  invoice it was against.
- **`invoice.create` with `capture: false` reported `captured: true`** on an offline payment.

## Tier prices were unusable in both directions

The write treated Magento's `200` carrying an error array as success: `set: true` with nothing
stored. The read decoded the **write** interface's field names (`customer_group`, `quantity`,
`price`) while the read interface returns `customer_group_id`, `qty` and `value`, so every read
came back zero. The storefront handles tier prices correctly when they are set directly, so the
whole failure was in the gateway.

This is the third appearance of the same shape in this codebase: an upstream that reports a
business failure inside a 200, or fields the gateway assumes rather than checks. The repair adds
a shared decoder rather than a fourth local patch.

## Operation unknown now has an exit

The production ledger held **eleven `order.create` rows in `unknown`** with `reconcile_after`
at infinity; the reconciler ran every minute and resolved none. There was no tool to query an
operation, so a caller told "poll the operation status" had nothing to poll.

`operation.get`, `operation.list` and `operation.dispose` close that. Disposal is a recorded
human judgement, not a state flip — `operation_unknown` means nobody knows whether the upstream
call happened, so `dispose` requires a note and records who decided what, then either marks it
applied, marks it not applied (releasing the derived key so a retry is safe), or requeues it for
the reconciler. Flipping the state without a judgement would launder uncertainty into
certainty.

Two related corrections came out of the same work: `order.create` had been recording the
**customer** id as the order id, so an operator reading an unknown row would look up an unrelated
order; and once that changed, the reconciler would have treated an existing customer as proof
that an order was placed, resolving a placement that never happened as applied. Both are guarded.

## Everything else

Ambiguous money outcomes now carry an explicit `retryable: false` instead of omitting the key.
`bulk_update` rejects duplicate and unknown SKUs instead of silently folding them and reporting
success. Upstream 400 diagnostics reach the error details, so a missing field no longer arrives
as "verify store_code and field values". The default RBAC policy binds an instance, and approval
requires a human identity rather than any verified token. Reports share one window convention, so
summary and analysis put a 23:30Z order on the same day, and `refunded_amount` is the document
total rather than a line subtotal.

The design-contract check, which had been red since v0.11.6, now runs against the documents that
exist — including dropping an assertion that demanded `platform.job.get`, a tool that was never
built.

## Testing

The live matrix is unchanged from v0.11.6: **112 pass, 7 soft, 1 fail, 3 skipped**, case for
case. Six of the fixes were spot-checked with real calls against a direct REST read, including
the P0, the comment path, the partial-refund arithmetic and the credit memo ceiling.

Full gate: `go test ./...` and `-race` clean, QA 19 pass with no skips, the design-contract check
green (115 tools, 22 ADRs), gofmt, vet, markdownlint, actionlint and the link check clean.

## Upgrade notes

No configuration changes and no new dependencies. The tool catalog grows from 102 to 105 with
the three `operation.*` tools.

**Behaviour changes worth knowing:**

1. **A partial refund no longer refunds shipping by default.** Pass `shipping_amount` to control
   it; remaining shipping is refunded only with the last units.
2. **`order.create` records `entity_type: customer`** in the operation ledger, with the order
   number in `upstream_ref` on success. Anything reading the ledger's entity columns should
   follow that.
3. **`bulk_update` now rejects** duplicate or unknown SKUs rather than silently dropping them.
