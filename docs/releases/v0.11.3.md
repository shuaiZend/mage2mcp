# v0.11.3 release notes

**Four defects the v0.11.2 live run exposed, fixed.** v0.11.2 shipped the fixes for the
first live run; continuing that run — once the customer-address failure was out of the
way — surfaced four more.

The Chinese test report that records all of them is
[`docs/audit/live-magento-test-report-v0.11.2-zh.md`](../audit/live-magento-test-report-v0.11.2-zh.md).

## Fixed

1. **`magento.customer.addresses` failed for any customer that has an address.** Magento
   returns a customer address's `region` as an object
   (`{region_code, region, region_id}`) while the order address returns a plain string.
   Both were decoded as a string, so the address array element was rejected and the tool
   reported "unreadable customer payload" — pointing at the envelope instead of the
   element. Earlier runs missed it because they used a freshly created customer with no
   addresses, and an empty array parses fine.
2. **`magento.inventory.unassign` never worked.** It called
   `DELETE /inventory/source-items`; Magento's MSI delete endpoint is
   `POST /inventory/source-items-delete`. The DELETE form is not a route.
3. **`magento.inventory.stock_source_unlink` never worked**, for the same reason:
   `DELETE /inventory/stock-source-links` instead of
   `POST /inventory/stock-source-links-delete`.
4. **`magento.inventory.stock_source_link` sent the wrong field name.** It used
   `position`; Magento requires `priority` and rejects the whole request with
   `"%fieldName is not supported"`, which surfaced as "verify store_code and field
   values" and hid the cause.
5. **`magento.customer.addresses.update` gave up on a store without a dedicated address
   route.** It now falls back to replacing the address through `PUT /customers/{id}`, the
   same way create already did.

## Why these survived the audit

Items 2 and 3 are the same failure mode as the order-placement bug in v0.11.2: the unit
tests asserted the **wrong** route, so the suite proved the implementation matched a
route that does not exist. A fake server built from the same wrong assumption cannot
catch it. What caught it was running against a real store and reading the 404.

## Testing

| Run | Pass | Soft | Fail | Skipped |
|---|---|---|---|---|
| v0.11.2 published image | 82 | 16 | 1 | 24 |
| After the `region` fix | 83 | 15 | 1 | 24 |
| **After all four fixes** | **91** | **7** | 1 | 24 |

The single hard failure is the demo store's missing custom-option route, an environment
limitation.

The configurable domain was verified for the first time: four harness payloads did not
match the tool schema, so `create`, `children`, `update` and `remove_child` had never
actually run. They now pass.

Every remaining soft failure is attributed in the report — an environment rule, a
deliberate rejection, or a harness data issue — with no unaccounted failure.

## Upgrade notes

No configuration changes and no new dependencies. `inventory.stock_source_link` now
sends `priority`; a caller that was passing `position` was always being rejected by
Magento, so nothing that worked can break.
