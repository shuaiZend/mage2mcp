# v0.11.4 release notes

**The money path, fixed.** Every release since v0.11.1 has been verified against a real
Magento store, but the part that matters most — placing an order and everything
downstream of it — never actually ran, because `order.create` failed first and the
invoice, shipment and credit-memo cases were skipped as downstream.

This release exercises that path for the first time and fixes six defects it found. All
six are the same class as the order-placement `POST`/`PUT` bug in v0.11.2: a route or a
response shape that was assumed rather than observed.

The full record is in
[`docs/audit/live-magento-test-report-v0.11.2-zh.md`](../audit/live-magento-test-report-v0.11.2-zh.md)
(Chinese), section 10.

## The root cause of LIVE-8

Magento's document-create routes answer with the new document's **id as a JSON scalar**,
not the document:

| Route | Actually returns |
|---|---|
| `PUT /carts/{id}/order` | `"8"` |
| `POST /order/{id}/invoice` | `"4"` |
| `POST /order/{id}/ship` | `"3"` |
| `POST /order/{id}/refund` | `"2"` |

The gateway decoded each as an object, the decode failed, and the failure was reported as
an unreadable response — so a **successful** write was recorded `operation_unknown` with
the caller told not to retry. The order existed; the gateway could not read its own
answer.

That also explains why the reconciler never helped: the ambiguous path was never taken.
The response carried no `reconcile` detail, which is what an order-placed-but-unreadable
outcome looks like, not an order-that-cannot-be-found.

## The six defects

1. **`order.create`** decoded the placement response as the order.
2. **`invoice.create`** did the same.
3. **`creditmemo.create`** did the same, and used `POST /creditmemos`, which is not a
   route; the route is `POST /order/{id}/refund`.
4. **`shipment.create`** used `POST /shipments`, also not a route; it is
   `POST /order/{id}/ship`.
5. **`shipment.get` and `creditmemo.get`** used plural read routes. Magento is
   inconsistent here: `GET /invoices/{id}` is plural, `GET /shipment/{id}` and
   `GET /creditmemo/{id}` are singular, and the plural forms are 404.
6. **`shipment.email` and `creditmemo.email`** had the same plural/singular split.

## Fix

`decodeCreatedDocumentID` accepts every shape Magento returns — a JSON string, a JSON
number, or an object carrying `entity_id` — and each create reads the document back, so
the caller receives the record rather than an id.

## Verified end to end on the demo store

| Step | Result |
|---|---|
| `order.create` | succeeds, returns the order |
| Same `idempotency_key` again | `replayed: true`, same order, **no duplicate** |
| `order.hold` / `unhold` / `email` / `cancel` | succeed |
| `invoice.create` | succeeds, `state: 2` |
| `shipment.create` | succeeds |
| `creditmemo.create` | succeeds |
| `invoice.get`/`list`, `shipment.get`/`list`, `creditmemo.get`/`list` | succeed |

## Test results

| Stage | Pass | Soft | Fail | Skipped |
|---|---|---|---|---|
| v0.11.3 published image | 91 | 7 | 1 | 24 |
| After the placement-response fix | 103 | 8 | 1 | 11 |
| After the document harness fix | 107 | 10 | 1 | 5 |
| **After the email-route fix** | **111** | **8** | 1 | **3** |

Twenty more cases pass and the skipped count fell from 24 to 3.

Every remaining soft failure is attributed in the report — an environment rule, a
deliberate rejection, or a harness data issue. The single hard failure is the demo
store's missing custom-option route.

## Why the suite did not catch any of this

The unit tests asserted the wrong routes and the wrong response shapes. A fake server
built from the same wrong assumption cannot catch it: it answers exactly as the
implementation expects. This is the third release in a row where the same failure mode
appeared — `POST` instead of `PUT`, `DELETE` instead of `POST ...-delete`, and now scalar
ids decoded as objects — and in every case the test agreed with the bug.

## Upgrade notes

No configuration changes and no new dependencies. Anything that calls
`order.create`, `invoice.create`, `shipment.create` or `creditmemo.create` will now
return the created record instead of `operation_unknown`, and idempotent replays return
the recorded result.
