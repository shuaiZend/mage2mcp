# v0.11.10 release notes

**The guidance round.** A second set of role tests asked a different question from the first:
not whether the tools can do the job, but whether the written guidance lets an agent do it
correctly. That mattered because the previous release replaced a 3,157-character instruction set
with 2,474 characters plus six prompts and a skill, and those words are now an agent's only
manual.

The reports are in [`docs/audit/guidance-round2/`](../audit/guidance-round2/), with the captain's
reasoning in [`captain-adjudication.md`](../audit/persona/captain-adjudication.md).

## One finding was not a documentation problem

`order.create` could put products nobody asked for into an order.

The customer cart route is **get-or-create**: calling it for a customer who already has an active
cart returns that cart. Two calls for one customer therefore share it, and whoever places first
takes both sets of items. Measured: three mixed orders in six concurrent rounds, none in the
serial control.

The decisive experiment did not involve concurrency at all. Items were left in a customer's cart
over REST, an order was placed **through the gateway** asking for one product, and the order came
back holding two. A residual cart — left by a call that died between adding items and placing the
order, or by a caller using REST directly — is carried into the next order.

That is a category worse than a wrong instruction: the call succeeds, the total is plausible, and
only the item list is wrong. It was noticed because a reader recognised a product they had not
ordered.

Two gates now. Before placing, the cart is read and must be empty; otherwise the call returns
`conflict` naming the count and the SKUs, and writes nothing — clearing another party's cart is
destructive and not the gateway's decision. Around that, calls for one customer are serialised
in-process. **The empty-cart gate is the one that holds across processes**; the lock is per
replica and the code says so, because a second replica needs a database lock.

The cart id now reaches the ledger result and the logs. Previously a mixed order could only be
investigated by reading the order's contents and guessing.

## The write flow has three steps, not two

The instructions said: call, receive a `confirmation_id`, resend with it. Following that literally
produces this:

```text
first call  → confirmation_required with a confirmation_id
resend      → confirmation_required: "confirmation has not been approved"
              (no details, no id, no next step)
```

An agent cannot infer that a human must run `mage2mcp-admin approve` in between, because nothing
said so. Both surfaces now name three steps, with the approval in the middle, and state what an
unapproved resend returns so the reader is not surprised by a response carrying nothing to act on.

## The money tools' audit rows could not be correlated

The earlier fix added the request id to the audit row the middleware writes. The self-ledgered
money tools — order create, invoice create and capture, credit memo, cancel, dispose — write their
own, and those are not built as an audit event in the money code at all: the ledger writes them in
the same statement that records the transition, and those `INSERT`s had no request id column.

So the calls that most need correlating were the only ones that could not be. The id now lives in
a small package both sides can import, and the ledger reads it from the context.

## The guidance was right on the main path and wrong at the edges

| What the text said | What is true | Consequence |
|---|---|---|
| `created_at` is "Store time" in the field description | UTC, as the instructions say | an accountant is off by an hour, and across a month boundary, by a period |
| revenue sums every order in the window | under truncation, only the scanned part | a report understates |
| the import terminal state is `complete` | `succeeded` | an agent polls forever |
| every CSV row needs `name` | a `sku,price` file is a valid bulk reprice | a workable batch is abandoned |
| `product.get` returns media and tier prices | it returns neither | they are silently skipped |
| create the children, then the parent | one call; pre-creating fails on an existing SKU | the recipe cannot run |
| refunding "the last refundable units" returns shipping | the scope is the **invoice**, not the order | full shipping refunded while items remain |

The last one is the subtlest: every other error makes the agent fail visibly and doubt itself.
That one lets it succeed, with the text appearing to support its reasoning, and the only symptom is
money refunded too early.

**The common cause is mine.** When the copy recipe was compressed, I verified that the checklist
existed, that the character budget was met and that the red lines survived. I did not verify that
the tools it names return those fields, that its steps run in order, that field descriptions agree
with the instructions, or that truncation and validation timing are mentioned at all. "Written" is
not "correct".

## An entire section had been lost

The paragraph on copying from a source that is not Magento — Shopify, WooCommerce, a marketplace —
was in the previous instructions and was in neither the instructions nor the prompt afterwards.

My ruling said to move the copy recipe out and keep a checklist naming what to discover. That
checklist covers Magento to Magento. The non-Magento paragraph was a different paragraph, nobody
owned it, and it disappeared. I verified the checklist survived; I did not verify that every
sentence of the old text had a new home.

## Guards

Three defects this round were "the text says something the code does not do" and nothing caught
them, so three guards now exist:

- `TestInstructionToolNamesResolve` resolves every tool name in the instructions against the
  registry, including the short form — a missing `magento.` prefix is exactly the shape of the
  error, and the previous version had the same class of mistake in a different name.
- `TestImportsPromptAndDescriptionAgree` reads the prompt and the tool description and asserts the
  shared facts in both directions, because these two disagreed and a reader cannot tell which to
  believe.
- `TestProductCopyPromptCarriesTheCopyRecipe` asserts twenty-one recipe facts and three negative
  ones, so old wording cannot return.

All are verified by revert: each assertion turns red when the sentence it protects is removed.

## Budgets are nearly exhausted

Measured in runes, `refunds.md` has two characters of headroom against its ceiling and
`write-contract.md` had twenty-one. Both needed new sentences this round, so both were compressed
rather than given a larger budget. A loaded skill is a resident cost for the client, and growth
should be a decision rather than an accident.

## Testing

`go test ./...` and `-race` clean, `local-ci.sh` passes end to end, golangci-lint reports nothing
with the output caps disabled, the design-contract check is green, and markdownlint, shellcheck,
actionlint and the link check are clean.

## Upgrade notes

No configuration changes and no new dependencies.

**One behaviour change, and it is deliberate:** `order.create` now fails with `conflict` when the
customer's cart is not empty, instead of placing an order that includes whatever was already in it.
If you were relying on the old behaviour, you were relying on a bug.

**The in-process lock is per replica.** A deployment with more than one server replica needs a
database lock for the same guarantee; the empty-cart gate still holds either way, turning a mixed
order into a refusal.

**A first-round finding is withdrawn:** SO-05, shipments arriving short, is Magento truncating a
quantity larger than the order. It was never a gateway defect; the real gap was that the
truncation was undocumented.
