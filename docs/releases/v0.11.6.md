# v0.11.6 release notes

**The semantic-layer pass.** Seven parallel domain tests asked not whether the routes exist
but whether the tools do what they say. They found 51 things; two of them were money.

The full record is in
[`docs/audit/semantic/FINAL-REPORT-zh.md`](../audit/semantic/FINAL-REPORT-zh.md) (Chinese),
with one report per domain and five cross-verification reports beside it.

## The two release blockers

`/order/{id}/ship` and `/order/{id}/refund` take their parameters at the **top level**. The
gateway wrapped them in `{"entity": {...}}`, which Magento ignores — so it received no
`items` and applied the whole order.

| Scenario | Before | After |
|---|---|---|
| Order of 2, refund 1 (with 10 shipping) | credit memo **78.00** (whole invoice) | **44.00** (34 + 10) |
| Order of 2, ship 1 | `total_qty` **2** (whole order) | **1** |

The invoice route was already correct, and that is exactly why this survived: the invoice
test passed, and it never occurred to anyone that its two siblings were shaped differently.

## Everything else

**Money and orders.** `order.cancel` reported `canceled: true` when Magento answered 200
with `false`. Address fallbacks dropped `region_id`. Credit memo `total_qty` leaked a zero.

**Security.** The default RBAC policy did not bind an instance, so a viewer could read
another store. Migration 000009 admits the approval audit row that the `decision`, `phase`
and `state` constraints all rejected — every approval had no audit trail at all.

**Audit trail.** A tool error returned as a result audited as succeeded. `request_id` never
reached the audit row or `_meta`. A replay did not validate its confirmation and left an
intent with no outcome. Ledger-gated outcomes carried no `request_id`, so money writes could
not be correlated.

**Honesty.** Rate-limit exhaustion reported as a timeout. Upstream 400 diagnostics discarded,
so "missing region_id" arrived as "verify store_code and field values". Inventory `unknown`
marked retryable. `bulk_update` folded duplicate SKUs silently. Import jobs said `succeeded`
for a partial batch.

**Startup.** The RBAC policy was built before the auth branch, so a multi-store deployment
with authentication **disabled** could not start.

## What the cross-checks caught

Five problems were found by someone other than the author, and two of them were regressions
introduced by the fixes themselves:

- a replay that validated its confirmation with `Consume`, pushing losers past the gate the
  concurrency contract depends on (caught by the QA suite);
- an RBAC policy built before the auth branch, blocking multi-store startup with auth off
  (caught by the agent writing the docs).

Two more were audit-trail gaps the original fixes did not cover, and they survived because
the covering test used a **read** tool that never enters the ledger path. A test can pass and
still not test the path you think it does.

## Testing

The live matrix on the demo store is unchanged from v0.11.5: **112 pass, 7 soft, 1 fail,
3 skipped**. Zero regression. The one hard failure is the store's missing custom-option
route; the seven soft failures are an environment rule, a deliberate rejection, or a harness
precondition, each attributed in the report.

Two cases that used to flip between runs now set up their own preconditions, so the matrix
is deterministic.

Full gate: `go test ./...` and `-race` clean, independent QA 18/0/0 with no skips, gofmt and
vet clean, markdownlint 131 files clean, link check clean.

## Upgrade notes

No configuration changes and no new dependencies.

**Two behaviour changes worth knowing:**

1. **A multi-store deployment with authentication disabled now starts.** It used to fail with
   an RBAC error even though RBAC was not in play. With authentication *enabled*, a module
   with more than one instance still refuses to start — that is deliberate, and
   `DefaultPolicyAllInstances()` is the explicit single-trust-domain opt-in.
2. **`idempotentHint` is now derived from the idempotency each tool description states.** 11
   write tools change from `false` to `true`. A client that retried on the annotation was
   being told the opposite of what the description said.

Approvals now write an audit row, which needs migration 000009 to be applied at startup.
