# 第二轮：照指引做（v0.11.9 生产）

第一轮问的是「**工具能不能干活**」。这一轮问的是「**写下的指引能不能让 agent 干对活**」。

v0.11.8 重写了 server instructions（3,157 → 2,474 字符，新增写契约与读语义），把商品复制
配方迁到 prompt，并发布了 6 个 prompt。v0.11.9 修了门禁与 `Escalate` 的 reason。

**这些文字现在是 agent 唯一的操作依据。** 如果它们漏了、含糊了、或与实际行为矛盾，agent 会
照着做错，而错误看起来是「agent 笨」而不是「文档错」。

## 方法：先读指引，再照做

每个岗位的第一步都是 `prompts/get` 取对应 prompt 的**全文**（用 MCP 客户端，不是读源码），
把它当作唯一手册，然后**照做，不凭经验跳过**。

如果某一步看起来多余，那正是要记录的信号——要么指引写错了，要么它在解释你没意识到的坑。

## 判定口径

每条记录必须落到三类之一：

| 判定 | 含义 |
|---|---|
| **一致** | guidance 说了，实际也是那样 |
| **缺失** | guidance 没说，但必须做（agent 会卡住或做错） |
| **矛盾** | guidance 说的与实际行为不同 |

## 与第一轮的关系

第一轮（`docs/audit/persona/`）发现了 85 条缺陷，v0.11.7 修了大部分。这一轮**不复测那些修复**
（除非它们与指引相关），而是问：**修好之后写下的说明，准不准。**

## 数据卫生

- 自建数据用 `R2-<域>-<时间戳>` 前缀
- 不修改 demo 店的既有商品/订单（`t50` 的 12 条 unknown 除外——那是真实运维任务）
- 涉及金额的操作必须 REST 直连回读核对
- 数字要绑定快照时间（并发 agent 会改数据）

## 环境事实：demo 店会重置，且抹掉 order id 序列

测试期间确认（t48 / t50 独立观察）：

- 上一轮（11-21）建的订单**全部消失**，库里只剩 2022-08-26 的两条 demo 订单
- 11-21 11:26 订单号到 `order/17`，16:38 又从 `order/3` 重新开始
- `MCPTEST-PROD-*` 商品 → not_found，而更早的 `G2-SO-1001` 仍在
- `customer 2..7` 全部 not_found；`inventory.sources` 只剩 `default`

**三条判读规则**：

1. **「现在查不到」不等于「当时没发生」**——重置会抹掉证据。依赖回查的结论必须绑定快照时间。
2. **「订单号不连续」不是丢单证据**——重置会重置序列。
3. 自建数据要尽快完成并回读，不要「先建后核」跨太久。

### 这意味着什么

本轮要修的都是「补一句必要说明」——例如退款运费的作用域（`refunds.md`）、写操作的三步流程
（`write-contract.md`）。而这两个文件的余量分别是 **2** 和 **21** 个字符。

**修法只能是压缩同文件的其他措辞，不能调预算。** 预算是 t21 有意定的（skill 是客户端的常驻成本，
增长应该是决策而不是意外）。

### 一个值得记的设计信号

预算定得「刚好够用」的后果是：**当内容需要变准确时，只能先删掉别的东西**。

t52 已经撞过一次——`product-copy.md` 当时只剩 69 字符，它整篇压缩重写到 3,952 才放下非 Magento
映射节。这次是对的（压缩而非调预算），但它说明：**准确性修正与预算上限会持续冲突**，需要有人
定期判断「哪些内容还值得占这个位置」。

如果后续还有修正放不下，正确做法是**报告冲突并说明取舍**，而不是悄悄调高预算或删掉别的事实。
